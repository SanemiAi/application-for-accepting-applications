# Архитектура системы учёта заявок

**Лабораторная работа №3.** Основа — требования из [docs/TZ.md](../TZ.md).

## 1. Выбранный вариант: слоистая архитектура

Рассматривались два варианта:

| Критерий | Слоистая (выбрана) | Микросервисная |
|---|---|---|
| Простота | Один исполняемый модуль, один деплой | Несколько сервисов, оркестрация |
| Тестируемость | Слои изолированы, легко тестировать сквозным сценарием | Сложнее: контрактные тесты между сервисами |
| Расширяемость | Достаточна для учебного проекта (новые роутеры/модели) | Избыточна на текущем масштабе |
| Стоимость внедрения | Docker Compose из двух контейнеров | Требует Kubernetes/брокеров — перебор |
| Соответствие учебному проекту | Да: вся логика прозрачна и читается за один сеанс | Нет: накладные расходы скроют предметную область |

**Аргументы «за» слоистую:** минимальная инфраструктура, явные границы ответственности,
простая проверка требований. **«Против»:** при росте нагрузки масштабируется хуже
микросервисов — для учебной нагрузки несущественно.

## 2. Слои и границы ответственности

| Слой | Компоненты | Ответственность | Не должен делать |
|---|---|---|---|
| Presentation / Controller | `app/routers/web_router.py`, `auth_router.py`, `tickets_router.py`, `admin_router.py`, шаблоны `app/templates/` | Принимает HTTP-запрос (форму или JSON), вызывает проверки, отдаёт HTML/JSON | Не содержит SQL и бизнес-решений о переходах статусов вне общих функций |
| Service (бизнес-правила) | `app/auth.py` (JWT, хэширование, `require_roles`), `check_access` / `apply_status` в `tickets_router.py` | Аутентификация, роли, права доступа к заявке, правила переходов статусов | Не рисует интерфейс и не работает с HTTP напрямую |
| Repository / Data Access | `app/models.py` (SQLAlchemy ORM), `app/database.py` (engine, сессии) | Чтение и изменение данных через ORM | Не принимает бизнес-решений |
| Database | PostgreSQL 16 (контейнер `db`) | Хранение, целостность (PK, FK, UNIQUE, NOT NULL) | Не содержит UI- и прикладной логики |

## 3. Основные модули

- **Пользователи** — `models.User`, регистрация/логин (`auth_router`), управление (`admin_router`).
- **Заявки** — `models.Ticket`, жизненный цикл (`tickets_router`, `web_router`).
- **Статусы** — константы и матрица переходов `models.Status` (`TRANSITIONS`).
- **Категории** — `models.Category`, CRUD в `admin_router`.
- **Комментарии** — `models.Comment`, добавление через API и веб.

```

│   │   ├── tickets_router.py   # /api/tickets — заявки, статусы, комментарии
│   │   ├── admin_router.py     # /api/admin — пользователи, категории
│   │   └── web_router.py       # / — HTML-страницы (cookie-сессия)
```

## 5. Ключевые классы/модули: назначение, вход, результат

| Модуль/класс | Назначение | Вход | Результат |
|---|---|---|---|
| `auth.get_current_user` | Извлекает пользователя из JWT | HTTP-заголовок Authorization | `User` или 401 |
| `auth.require_roles` | Ограничивает эндпоинт ролями | Список ролей | Пропуск или 403 |
| `tickets_router.apply_status` | Проверяет переход статуса | Заявка, новый статус, роль | Статус изменён или 400 |
| `tickets_router.check_access` | Проверяет доступ к заявке | Пользователь, заявка | Пропуск или 403 |
| `web_router.get_web_user` | Пользователь из cookie-сессии | Cookie `access_token` | `User` или None (редирект на /login) |

## 6. Почему архитектура подходит проекту

- Ролевая модель и переходы статусов — чистые бизнес-правила; они собраны в одном месте
  (`auth.py`, `check_access`, `apply_status`) и общие для REST API и веб-интерфейса,
  поэтому правила невозможно «обойти» через другой интерфейс.
- Доступ к данным только через ORM — переход с PostgreSQL на SQLite для лабораторной №5
  не потребовал переписывания логики.
- Два контейнера (app + db) под Docker Compose — воспроизводимая среда для проверки
  преподавателем одной командой.
