## Лабораторная №1 — анализ требований

1. **Задача:** по краткому описанию предметной области получить роли, функциональные и
   нефункциональные требования, сущности и критерии приёмки для «Системы учёта заявок».
2. **Модель:** Kimi (Kimi Code).
3. **Промпт (структурированный вариант):** «Нужно написать приложение приёма и подачи заявок
   с ролями: Заявитель, Оператор, Исполнитель, Администратор. Заявитель может создать заявку,
   просматривать свои заявки, дополнять описание или комментарий. Оператор может просматривать
   заявки, уточнять категорию и описание, назначать исполнителя, менять статус. Исполнитель может
   видеть назначенные ему заявки, брать их в работу, отмечать выполнение, оставлять комментарии.
   Администратор может управлять пользователями и категориями, назначать роли, просматривать и
   изменять все заявки. В заявке должны быть указаны — уникальный номер, тема, описание, дата подачи,
   категория, статус, исполнитель, заявитель, комментарии. Статусы заявки — Новая, В работе,
   Выполнена, Закрыта. На базе данных PostgreSQL.»
4. **Почему такой промпт:** заданы роли и их права перечнем, состав полей заявки и статусов —
   это сразу фиксирует границы системы и снимает двусмысленность.
5. **Почему такая модель:** агентская модель с доступом к проекту — результат сразу проверяется
   кодом и запуском, а не только текстом.
6. **Результат ИИ:** роли, 15 функциональных и 5 нефункциональных требований, 6 сущностей,
   сценарии использования и критерии приёмки (оформлены в `docs/TZ.md`).
7. **Проверка:** каждое требование сопоставлено с реализованной функцией приложения;
   формулировки «Система должна…» перепроверены на противоречия; диаграмма Use Case сверена
   с текстом ролей.
8. **Собственная доработка:** свободный (короткий) вариант промпта дал общий ответ без границ
   прав ролей; выбран структурированный. Вручную уточнил требование: закрывать заявку может
   и заявитель-владелец (подтверждение выполнения) — в исходной постановке это было неявно.
9. **Вывод:** структурированный промпт с ролями и перечнем полей дал результат, почти готовый
   к использованию; главная работа — проверка неявных мест (кто закрывает заявку).

## Лабораторная №2 — Git

1. **Задача:** организовать репозиторий: структура, `.gitignore`, осмысленные коммиты, ветка
   develop, слияние в main.
2. **Модель:** Kimi (Kimi Code).
3. **Промпт:** «Можешь загрузить это всё на мой репозиторий в GitHub, вот ссылка…» + «Теперь
   закончи приложение, чтобы оно соответствовало требованиям файла (лабораторные 1–5)».
4. **Почему такой промпт:** задача поставлена целиком, модель сама разбила её на этапы
   (коммиты по этапам: docs, chore, feat).
5. **Почему такая модель:** команды Git выполняются прямо в окружении проекта, результат
   проверяется `git log` и `git status`.
6. **Результат ИИ:** `.gitignore` для Python-стека, последовательность коммитов по этапам,
   ветка develop со слиянием в main.
7. **Проверка:** история коммитов просмотрена (`git log --oneline`, `git branch`); убедился,
   что в репозитории нет паролей и токенов (секреты — только переменные окружения).
8. **Собственная доработка:** сообщения коммитов привёл к рекомендованному в методичке
   формату (`docs:`, `chore:`, `feat:`); удалённую отправку (push) выполнил сам с собственным
   Personal Access Token — токен в нейросеть не передавался.
9. **Вывод:** ИИ полезен для последовательности команд и шаблона `.gitignore`; операции,
   затрагивающие удалённый репозиторий, осмысленно выполнять вручную.

9. **Вывод:** ревью ИИ нашло дефект, который я пропустил (конфликт маршрутов проявлялся

## Лабораторная №4 — интерфейс

1. **Задача:** экраны системы: вход, список заявок, создание, карточка, редактирование,
   поиск/фильтрация, статусы, ошибки и подтверждения.
2. **Модель:** Kimi (Kimi Code).
3. **Промпт:** «В приложении есть интерфейс?» → «Первый вариант [серверные HTML-страницы],
   начнём с базового набора» → затем доработка до полного набора экранов по методичке.
4. **Почему такой промпт:** сначала уточнён вариант реализации (серверные страницы в том же
   приложении против отдельного SPA) — это определило всю архитектуру интерфейса.
5. **Почему такая модель:** генерация шаблонов Jinja2 и контроллеров с немедленной проверкой
   в запущенном приложении.
6. **Результат ИИ:** 6 экранов (логин, список с поиском и фильтрами, создание, карточка с
   действиями по ролям, редактирование, пустые состояния и баннеры ошибок), цветные метки
   статусов, подтверждение закрытия заявки.
7. **Проверка:** сквозной автотест `tests/e2e_check.py` (26 проверок) прогоняет все роли через
   веб-формы: логин, подача, назначение, взятие в работу, выполнение, дополнение, закрытие,
   фильтры и поиск, запрещённые действия.
8. **Собственная доработка:** по UX-чек-листу: добавлены пустые состояния списка
   («ничего не найдено» со ссылкой сброса), явные сообщения об ошибках в карточке заявки
   вместо JSON-страниц ошибок, подтверждение опасного действия (закрытие) через диалог.
9. **Вывод:** чек-лист ИИ пригодился как приём ревизии собственного интерфейса: три пункта
   (пустые состояния, тексты ошибок, подтверждения) действительно были упущены в первой версии.

## Лабораторная №5 — база данных

1. **Задача:** ER-модель, schema.sql, seed.sql, SQLite-база, демонстрационные запросы
   (5 INSERT / 5 SELECT / 2 UPDATE / 2 DELETE, 3 WHERE, 2 JOIN).
2. **Модель:** Kimi (Kimi Code).
3. **Промпт:** требования лабораторной №5 из методички (таблицы Users, Requests, Statuses,
   Categories, Comments + Roles; внешние ключи; нормализация; скрипты и запросы).
4. **Почему такой промпт:** задан явный минимум таблиц и запросов — модель не «угадывает»
   объём, а покрывает чек-лист.
5. **Почему такая модель:** скрипты выполняются немедленно (SQLite встроен в Python),
   результат проверяется на реальных данных.
6. **Результат ИИ:** нормализованная схема из 6 таблиц (роли и статусы вынесены в справочники),
   `sql/schema.sql` с PK/FK/UNIQUE/NOT NULL, `sql/seed.sql` с осмысленными тестовыми данными,
   `sql/queries.sql`, готовая `database/tickets.db` и `docs/sql_results.txt`.
7. **Проверка:** скрипт `tools/build_sqlite.py` пересоздаёт базу с нуля и выполняет все запросы;
   результаты SELECT сверены с ожиданиями (например, JOIN выдаёт заявки с ФИО участников,
   после DELETE проверочный COUNT даёт 0). Внешние ключи включены (`PRAGMA foreign_keys = ON`).
8. **Собственная доработка:** изменил демонстрационный UPDATE — первоначально он переводил
   единственную заявку «В работе» в «Выполнена», и итоговый SELECT с GROUP BY возвращал пустой
   результат; заменил на закрытие другой заявки, чтобы запрос-отчёт остался показательным.
   Хэши паролей в seed — демонстрационные заглушки, реальные секреты в скрипты не включал.
9. **Вывод:** сгенерированный SQL требует прогона на данных: семантически допустимый запрос
   может дать пустой/бессмысленный результат из-за порядка демонстрационных операций.

### Запись 2 — диагностика неудачного теста

1. **Дата и задача:** 10.11.2026. Объяснить падение
   `test_complete_without_take_rejected` (ожидал 400, получил 403).
2. **Модель:** Kimi (Kimi Code).
3. **Почему выбран этот вариант:** нужен анализ именно нашего кода эндпоинта
   (порядок проверок в complete_ticket), а не общая теория HTTP-кодов.
4. **Полный промпт:** «Тест ждёт 400 при complete без take, но API возвращает 403.
   Фрагмент: POST /api/requests/{num}/complete от исполнителя по неназначенной
   новой заявке → 403 «Заявка не назначена вам». Объясни причину и предложи,
   как должен выглядеть корректный тест перехода статуса».
5. **Краткий результат:** модель указала порядок проверок в эндпоинте: сначала
   «заявка назначена вам?» (403), потом «статус В работе?» (400) — значит для
   проверки 400 заявку нужно сначала назначить этому исполнителю.
6. **Что принято/отклонено:** принято — тест переписан: назначение через оператора,
   затем complete → 400; исходный сценарий оформлен отдельным тестом на 403.
7. **Самостоятельная проверка:** повторный прогон всего набора — 23 passed,
   оба сценария (403 и 400) подтверждены.
8. **Вклад студента:** зафиксировал вывод в test_summary.md: поведение API
   осознанное, контракт задокументирован в отчёте.
