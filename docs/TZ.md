# Техническое задание: Система учёта заявок

**Дисциплина:** Технологии разработки программного обеспечения
**Проект:** сквозной учебный проект лабораторных работ №1–5

---

## 1. Назначение и описание проблемы

В организации сотрудники подают служебные обращения (поломка оборудования, вопросы кадров,
снабжение и т. п.) в произвольной форме: по электронной почте, в мессенджерах, устно.
Без единой системы обращения теряются, непонятно, кто за них отвечает, на каком они этапе,
невозможно проконтролировать сроки и качество исполнения.

**Система учёта заявок** решает эту проблему: каждое обращение регистрируется с уникальным
номером, получает категорию и статус, назначается конкретному исполнителю и проходит
контролируемый жизненный цикл от подачи до закрытия. Все участники видят только те заявки
и действия, которые соответствуют их роли.

## 2. Роли пользователей и их права

| Роль | Разрешённые действия |
|---|---|
| **Заявитель** | Создать заявку; просматривать свои заявки (поиск, фильтры); дополнять описание своей заявки; оставлять комментарии; подтвердить выполнение (закрыть заявку) |
| **Оператор** | Просматривать все заявки; уточнять тему, категорию и описание; назначать исполнителя; менять статус по разрешённым переходам; комментировать; закрывать выполненные заявки |
| **Исполнитель** | Видеть назначенные ему заявки; брать новую заявку в работу; отмечать выполнение (с комментарием); оставлять комментарии |
| **Администратор** | Управлять пользователями (создание, смена роли, сброс пароля); управлять категориями; просматривать и изменять любые заявки; все действия оператора |

## 3. Функциональные требования

1. Система должна регистрировать заявку с автоматически присваиваемым уникальным номером вида `З-000001`.
2. Система должна хранить в заявке: номер, тему, описание, дату и время подачи, категорию, статус, исполнителя, заявителя.
3. Система должна поддерживать 4 статуса заявки: «Новая», «В работе», «Выполнена», «Закрыта».
4. Система должна допускать только переходы статусов: Новая → В работе → Выполнена → Закрыта; прочие переходы отклоняются с сообщением об ошибке.
5. Система должна хранить не менее 4 категорий заявок и позволять администратору управлять ими.
6. Система должна аутентифицировать пользователей по логину и паролю (JWT-токен; для браузера — cookie-сессия).
7. Система должна ограничивать доступ к заявкам и действиям в соответствии с ролью пользователя.
8. Система должна позволять оператору и администратору назначать заявке исполнителя — только пользователя с ролью «Исполнитель».
9. Система должна позволять исполнителю брать новую неназначенную заявку в работу и отмечать назначенную заявку выполненной.
10. Система должна позволять заявителю дополнять описание своей заявки с пометкой «[Дополнено заявителем]».
11. Система должна хранить комментарии к заявке с указанием автора и времени.
12. Система должна предоставлять поиск заявок по номеру/теме и фильтрацию по статусу и категории.
13. Система должна визуально различать статусы заявок (цветные метки) и показывать сообщения об ошибках; опасные действия (закрытие заявки) требуют подтверждения.
14. Система должна позволять администратору создавать пользователей, назначать им роли и сбрасывать пароли.
15. Система должна предоставлять REST API (для интеграций) и веб-интерфейс (для работы в браузере) с одинаковыми правилами доступа.

## 4. Нефункциональные требования

1. **Удобство использования:** веб-интерфейс на русском языке; из каждого экрана понятен следующий шаг; пустые состояния и ошибки снабжены пояснениями.
2. **Надёжность:** данные хранятся в PostgreSQL; целостность обеспечивается первичными и внешними ключами, ограничениями NOT NULL/UNIQUE; запрещённые переходы статусов невозможны.
3. **Производительность:** список заявок и карточка заявки открываются менее чем за 1 секунду при объёме до 10 000 заявок; поля `number`, `username` проиндексированы.
4. **Безопасность:** пароли хранятся только в виде хэша (bcrypt); аутентификация по JWT с ограниченным сроком действия; секреты задаются переменными окружения и не хранятся в репозитории.
5. **Сопровождаемость:** код разделён на слои (роутеры / бизнес-правила / модели / шаблоны); проект разворачивается одной командой `docker compose up --build`; конфигурация вынесена в переменные окружения.

## 5. Сущности предметной области

1. **Пользователь** — логин, пароль (хэш), ФИО, роль.
2. **Заявка** — номер, тема, описание, дата подачи, категория, статус, заявитель, исполнитель.
3. **Статус** — один из четырёх: Новая, В работе, Выполнена, Закрыта.
4. **Категория** — название (Техподдержка, Снабжение, Административный вопрос, Кадровый вопрос, ИТ-оборудование).
5. **Комментарий** — текст, автор, дата и время, привязка к заявке.
6. **Роль** — одна из четырёх: Заявитель, Оператор, Исполнитель, Администратор.

## 6. Сценарии использования (Use Case)

Диаграмма: [docs/use_case.png](use_case.png).

1. **UC-1. Подача заявки.** Заявитель входит в систему → «Новая заявка» → заполняет тему, описание, выбирает категорию → система присваивает номер и статус «Новая».
2. **UC-2. Обработка заявки оператором.** Оператор открывает список всех заявок → фильтрует по статусу «Новая» → открывает заявку → уточняет категорию/описание → назначает исполнителя.
3. **UC-3. Выполнение заявки.** Исполнитель видит назначенные заявки → берёт заявку в работу (статус «В работе») → по завершении отмечает выполнение с комментарием (статус «Выполнена»).
4. **UC-4. Закрытие заявки.** Заявитель проверяет результат → подтверждает закрытие (статус «Закрыта»); при необходимости — оператор или администратор.
5. **UC-5. Обсуждение заявки.** Любой участник с доступом к заявке добавляет комментарий; история сохраняется в карточке заявки.
6. **UC-6. Администрирование.** Администратор создаёт пользователя, назначает ему роль; добавляет/переименовывает категории.

## 7. Критерии приёмки

1. Проект разворачивается командой `docker compose up --build` без дополнительной настройки; веб-интерфейс доступен на http://localhost:8000, документация API — на /docs.
2. Реализованы 4 роли с разграничением прав: заявитель не видит чужие заявки, исполнитель — только назначенные, административные функции недоступны остальным ролям (проверено автоматическим сквозным сценарием `tests/e2e_check.py`: 26/26 проверок).
3. Заявка содержит все поля из п. 3.2; номер уникален и присваивается автоматически.
4. Невозможно выполнить запрещённый переход статуса (например, «Новая» → «Закрыта») — система возвращает ошибку.
5. В списке заявок работают поиск по номеру/теме и фильтры по статусу и категории.
6. Категорий в системе не менее 4; администратор может добавлять новые.
7. Все артефакты (ТЗ, диаграммы, SQL-скрипты, код) опубликованы в Git-репозитории с историей осмысленных коммитов.
