## BUG-01 — Ошибка 422 при поиске с невыбранной категорией

- **Среда и версия:** http://localhost:8000, коммит `b3f9098` (develop), Chromium.
- **Шаги воспроизведения:**
  1. Войти любым пользователем.
  2. В поле поиска ввести текст, не выбирая категорию в фильтре.
  3. Нажать «Найти».
- **Ожидаемый результат:** список отфильтруется по поисковому запросу;
  пустые значения фильтров игнорируются.
- **Фактический результат:** страница «Ошибка валидации данных» (HTTP 422) —
  браузерная форма отправляет `category_id=` (пустая строка), параметр
  объявлен как `Optional[int]`, пустая строка не парсится в число.
- **Важность:** **High** — основной пользовательский сценарий (поиск) недоступен
  при самом частом состоянии фильтров.
- **Доказательство:** `curl "http://localhost:8000/?q=test&status=&category_id=&priority="`
  → HTTP 422 (до исправления); после — HTTP 200.
- **Исправление:** параметр принимается строкой и конвертируется только при
  числовом значении (`app/routers/web_router.py`), коммит `81920f6`.
- **Статус:** **исправлен, повторно проверен** — регрессионный тест
  «Поиск с пустыми фильтрами (форма браузера)» в `tests/e2e_check.py`
  и автотест `test_regression.py::test_search_empty_filters_ok` (ЛР №10).

## BUG-02 — Поиск не находил заявки по названию категории

- **Среда и версия:** http://localhost:8000, коммит `81920f6` (develop), Chromium.
- **Шаги воспроизведения:**
  1. Войти администратором.
  2. Ввести в поиск «Снабжение» (название существующей категории, в таблице
     есть 3 такие заявки).
  3. Нажать «Найти».
- **Ожидаемый результат:** найдены заявки категории «Снабжение» — пользователь
  ищет по тому, что видит в таблице.
- **Фактический результат:** «По заданным условиям ничего не найдено» — поиск
  вёлся только по номеру, теме и описанию.
- **Важность:** **Medium** — функция работала, но поведение противоречило
  ожиданиям пользователя и фактически делала поиск бесполезным по видимым полям.
- **Доказательство:** скриншот пустого результата (диалог с пользователем);
  после исправления: поиск «Снабжение» → З-000002, З-000008, З-000011
  (`evidence/tc05_search_category.png`).
- **Исправление:** поиск расширен на название категории, ФИО исполнителя и
  заявителя (веб и API), коммит `512abb0`.
- **Статус:** **исправлен, повторно проверен** — тест-кейс TC-05,
  автотесты `test_regression.py::test_search_by_category_name` (ЛР №10).

## BUG-03 — Авторизация в Swagger UI не работала (неверный tokenUrl)

- **Среда и версия:** http://localhost:8000/docs, коммит `512abb0` (develop), Chromium.
- **Шаги воспроизведения:**
  1. Открыть /docs, нажать «Authorize», ввести admin/admin123.
  2. Выполнить любой защищённый запрос, например GET /api/requests.
- **Ожидаемый результат:** запрос выполняется с Bearer-токеном, HTTP 200.
- **Фактический результат:** HTTP 401 «Not authenticated» — Swagger отправлял
  форму логина на `/auth/login`, тогда как эндпоинт смонтирован на `/api/auth/login`;
  токен не выдавался.
- **Важность:** **High** — интерактивная проверка API из документации
  (основной сценарий ЛР №7) была невозможна.
- **Доказательство:** скриншоты Swagger с ответом 401 до исправления;
  после исправления — `docs/screenshots_lab7/03_get_requests_200.png`
  (HTTP 200, Bearer-токен в curl-представлении запроса).
- **Исправление:** `tokenUrl="/api/auth/login"` в `app/auth.py`, коммит `805ae00`.
- **Статус:** **исправлен, повторно проверен** — скриншоты Swagger с кодами
  200/201/204/404/422, автотест `test_regression.py::test_openapi_token_url` (ЛР №10).
