# План тестирования — ЛР №9

## Объект и версия

- **Объект тестирования:** «Система приёма и подачи заявок» — веб-приложение + REST API
  (FastAPI + PostgreSQL 16, Docker Compose).
- **Версия приложения:** 1.1.0 (OpenAPI `info.version`), коммит `805ae00` ветки `develop`.
- **Дата проверки:** 10.11.2026.

## Тестовая среда

| Параметр | Значение |
|---|---|
| Адрес локального стенда | http://localhost:8000 |
| Адрес развёрнутой версии (ЛР8) | http://192.168.1.101:8000 |
| ОС | Windows 10/11 (x64) |
| Браузер/инструменты | Chromium (Playwright), curl 8.x, Swagger UI `/docs`, Python 3.15 |
| Запуск | `docker compose up --build -d` (контейнеры `ticket_system-app-1`, `ticket_system-db-1`) |
| Тестовые данные | `docker compose exec app python tools/seed_demo.py` — 6 пользователей, 5 категорий, 12 заявок |
| Тестовые учётные записи | `admin` (администратор), `olga` (оператор), `igor`/`petr` (исполнители), `ivan`/`maria` (заявители). Пароли в репозитории не публикуются — задаются локально через `.env` (`ADMIN_PASSWORD`, `SEED_DEMO_PASSWORD`) |

## Что проверяется

- Пользовательские сценарии по ТЗ (`docs/TZ.md`): создание, просмотр, редактирование,
  смена статуса, назначение исполнителя, комментарии.
- Поиск и фильтрация списка заявок (номер/тема/описание/категория/ФИО; статус, категория, приоритет).
- Ролевая модель: заявитель, оператор, исполнитель, администратор; доступ без авторизации.
- Валидация входных данных и обработка ошибок (веб-страницы и коды API).
- REST API: контракт эндпоинтов `/api/requests`, справочники, HTTP-коды, формат ошибок.
- Согласованность UI ↔ БД ↔ API: данные, созданные через интерфейс, читаются через API и наоборот.

## Что не входит в проверку

- Нагрузочное тестирование и производительность.
- Безопасность (пентест, устойчивость к атакам) — только базовые проверки доступа.
- Административные сценарии управления пользователями сверх смоук-проверки ролей.
- Кроссбраузерность (тестирование ведётся в одном браузере).

## Виды тестов

Позитивные функциональные, негативные, граничные значения, роли и доступ,
интеграционные (UI + БД + API), API-тесты (коды ответов, формат ошибок).

## Критерии начала

- Приложение поднято по README, `GET /health` возвращает `{"status": "ok"}`.
- Тестовые данные загружены, тестовые учётные записи доступны.

## Критерии завершения

- Все тест-кейсы из `test_cases.md` выполнены, у каждого зафиксирован фактический
  результат и статус (PASS/FAIL/BLOCKED) с доказательством.
- Все найденные дефекты оформлены в `bug_reports.md`; исправленные — повторно проверены.
- API-проверки сохранены (`api_checks.txt`, коллекция Postman).

## Порядок работы

1. Прогон ручных сценариев через веб-интерфейс (Chromium) с фиксацией скриншотов.
2. Проверка API через curl/Swagger UI (успех, ошибочные данные, отсутствующий объект).
3. Интеграционные проверки согласованности UI ↔ API ↔ БД.
4. Оформление дефектов, повторная проверка после исправлений.
5. Итоговая сводка результатов.
